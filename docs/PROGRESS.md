## 一、接入 QQ

**做了什么**：你在手机 QQ 上私聊"大肥鱼"，它在电脑上收到并用同一个人格回你。

**方法**：

- 用 **NapCat** 把 QQ 协议转成 **OneBot 11** 标准接口。
- **收**：用 HTTP 上报（`httpClients` 指向 `127.0.0.1:8080/event`，`messagePostFormat: "array"`），
  我们自己起一个 `ThreadingHTTPServer` 接。**收到就入队并立刻回 204**，真正处理在单线程队列里
  按到达顺序跑——NapCat 的 `baseTimeout` 只有 10 秒，等处理完再应答会被判超时重推，
  那样同一条消息会回两遍。
- **发**：反向调 NapCat 的 HTTP API（`/send_private_msg`，文本直接发，图片用 array 段发）。
- 全程只用标准库：`http.server` 收、`urllib.request` 发，没有 aiohttp/requests 之类。
  好处是换机器不用装依赖，坏处是并发靠线程池。

## 二、只跟你一个人聊

**做了什么**：别人私聊它不理。

**方法**：`ALLOW_USER_ID` 白名单，事件入口第一道判断，不匹配直接丢弃并写一条
`忽略非白名单用户 <id>` 日志。这个判断在解析之后、任何 LLM 调用之前，所以陌生人不花钱。

## 三、不重复回复

**做了什么**：NapCat 有时会重复上报同一条消息。

**方法**：用 QQ 的 `message_id` 做幂等键，入库 `INSERT OR IGNORE` + 唯一索引；
`has_qq_msg_id()` 先查再处理。同一 `message_id` 第二次进来直接跳过。

## 四、长期记忆（M2 P1）

**做了什么**：你说过的事它记得，聊到相关的会自然带出来。

**方法**：

1. **存储**：`cards` 表，一条记忆 = `kind`（身份/偏好/事实/事件/琐事）+ `summary`（≤40 字）+ `detail` + `entities` + `importance`。
2. **权重**（决定"现在什么最该被想起"）：

   ```
   weight = importance × (0.6 + 0.4 × freq) × (0.2 + 0.8 × recency)
   freq   = 命中次数 / 最大命中次数      （越常被提起越靠前）
   recency = 0.5 ^ (age_days / 30)      （30 天半衰期）
   ```

3. **抽取**：每轮对话后异步调一次模型，喂"已有记忆 + 最近对话"，
   要它输出受控 JSON（只允许 `add` / `update`，`delete`/`archive` 一律丢弃），单次最多 5 条。
   去重用 `SequenceMatcher` 相似度判重，不重复入库。
4. **注入**：把权重 > 0.15 的卡片按权重排序，塞进 system prompt，有字符预算截断。
   命中一次记一次 `hit_count`（同一天只算一次）。
5. **压缩**：上下文太长时，把较早的消息压成一段摘要，保住近期原文。
6. **记忆本（可改）**：`/memory` 按权重列前 20 条；`/memory add 内容` 手动加一条
   （`kind=fact`、`importance=0.6`）；`/memory edit 编号 新内容` 改摘要；
   配合已有的 `/forget`（删，关键词批量要 `confirm`）、`/pin` `/unpin`（钉住/松开）。
   自动抽取会记错也会漏，能改才叫记忆本。
7. **做梦（M2 P3）**：每天 `DREAM_AT`（默认 23:30）整理一次，错过就启动时补跑
   （判断"今天的目标钟点过了还没做"或"距上次超 20 小时"）。
   喂"上次记忆本 + 现有卡片 + 这段对话"，一次模型调用产出：
   **重写后的记忆本**（写 `data/journal.md`，原子替换）和**卡片操作**
   （只允许 `add` / `merge` / `reweight`，`delete` 直接丢弃）。
   `merge` = 源卡 `status='archived'`、detail 合并、命中次数累加——归档不是删除。
   每次记一条 `dream_log`（看了几条消息、增删改多少、记忆本字数、成功与否）。
   记忆本会以 `【记忆本】` 段注入 system prompt，预算 `JOURNAL_CHAR_BUDGET`（默认 1200 字）。
   `/journal` 看全文，`/dream` 手动整理一次。
8. **原话召回**：每轮对话把这句话切成三元片段（FTS trigram）走 `bm25` 召回，
   两字词（"香菜""火锅""加班"）trigram 索引不到，再用最近 8000 条消息的有界 `LIKE` 兜底；
   命中的原话以「他以前说过的原话」注入 system prompt，最多 `RECALL_MAX_MESSAGES`（默认 3）条。
   卡片记的是结论，这层记的是"他当时怎么说的"。实测在真实库上 <1ms。
9. **待确认事实**：抽取和做梦写出的卡片 `confirmed=0`，注入时单独成块
   （「听来的、还没核实的（别当事实说）」），且**不涨权重**（被注入 ≠ 变可信）；
   `/memory` 列表标 `·待确认`，`/memory ok 编号` 转正。手动 `/memory add` 直接算确认。
   **自动转正**：同一条事实隔天又被观察到（抽取的相似度去重命中 / 做梦总结出同样的摘要），
   旧卡自动 `confirmed=1`——"隔天又说了一遍"本身就是证据；同一天里说两遍不算。
10. **日摘要**：每天把流水压成一页 `data/daily/YYYY-MM-DD.md`（150~300 字，只记事实）。
   为什么需要：卡片记的是**结论**（"他不吃香菜"），原话召回只能拿**单句**，
   "上周发生了什么"这种问题两层都答不上——中间缺一层按天记的经过。
   启动时补最近 `DIGEST_CATCHUP_DAYS`（默认 3）天缺的，文件存在就不再生成（幂等）。
   最近几天的摘要以「最近几天（摘要）」注入 system prompt，预算 `DIGEST_IN_PROMPT_CHARS`（默认 600 字）。
   `/digest` 看今天、`/digest 昨天`、`/digest 周` 看一周。
11. **导出**：`/export` 写一份 `data/exports/export-<时间>.md`，含统计、记忆卡片（标出待确认）、
   未到的事件、最近两周摘要、最近 200 条对话。数据不能只"存在数据库里"。

**为什么这么做**：不存全量对话向量（本地跑不动 embedding，也贵），
用"卡片 + 权重"这种可解释的结构，你能直接看到它记了什么、为什么想起来。

## 五、人格

**做了什么**：18 岁的女友"大肥鱼"，娇小、害羞、依赖，需要被照顾。

**方法**：`prompts/system.md` 一份纯文本提示词，锁死说话风格、字数、亲密分寸、禁止事项（不装拍照、不写露骨内容）。
每次请求拼成 `system(prompt + 记忆块 + 原话召回 + 日摘要 + 此刻状态) + 历史消息`。
人格完全靠提示词，不微调、不换模型。完整设定存档在 `docs/persona/dafeiyu.md`。

**v2 的两点取舍**：

1. **"依赖"做成软的**：拿不定主意就问、要他来定，但不查岗、不翻旧账、不拿情绪绑人——
   会绑人的依赖两周就让人烦。
2. **亲密有边界**：牵手、抱抱、说想他可以；露骨内容不写，遇到就羞涩岔开。
   一半是人设（娇羞写露骨会崩），一半是账号安全（QQ 对这类内容封号）。

**v3：修"木头味"**。v2 上线后用户反馈"像机器人、而且跟旧人格没区别"。查下来两个原因：

1. **形容词没法执行**："娇小软和""依赖他"这类词，模型只能翻译成它自己那套
   "温柔女友"腔，而旧人格的"温顺懂事"翻出来是同一个腔。换形容词当然没变化。
2. **结构模板**：v2 几乎每条回复都是"唔…… + 陈述 + 空行 + 关心/反问"，
   八条里六条如此；"头发总画歪"复读三次；他累了永远是"关心+指令"。

改法（参考两套写卡方法论：把声音拆成 voice anchor / lived pressure / register envelope /
variability budget，属性写成行为锚点而不是形容词）：

- 每条硬规则都可检验：不许每句"唔"开头、不许每条两段式、不许空行、
  不许复述他的话再说感受、不许复读同一个细节、关心要具体到笨。
- 给样品对话（学手感、不照抄），样品本身就是"长度/形态都在变"的示范。
- 引擎侧一起修：兜底话术从 1 句变成 4 句随机（原来那句连着出现四次，用户以为是她的话）；
  连续空行压成单换行。

**验证**：同一组 6 句输入，旧/新 prompt 各跑一遍真模型，统计形态：

| 指标 | v2 | v3 |
|---|---|---|
| 以"唔"开头 | 4/6 | 0/6 |
| 平均字数 | 35 | 17 |
| 每条都"关心+反问" | 几乎全是 | 一半不是 |

来源：[表达校准包策略](https://raw.githubusercontent.com/XucroYuri/how-to-make-script/master/docs/expression-lens-policy-zh.md)、
[莉娅的酒馆写卡方法](https://github.com/feverZHONG/liya-sillytavern-cards)。

**踩到的坑：她会学自己说过的旧话**。改完 prompt 先在无历史的真模型上验证，很好；
接进机器人（带 20 轮历史）立刻退回旧模板——上下文里她那 20 条旧回复，
比系统提示的权重大得多。所以**换人格、换声音之后必须 `/reset`**（原文不删、长期记忆保留），
否则旧语气会一直传染。这一条是数据层面的，光改提示词救不回来。
另外顺手修了个真的"机器人味"来源：兜底话术原本只有一个常量，
API 挂掉那阵它连着发了四次一模一样的话。

## 六、表情包图库（M3）

**做了什么**：你发表情包，它收藏起来，之后聊天会用。

**方法**：

1. **识别**：OneBot 的 `image` 段里 `sub_type == 1`，或 summary 含"表情/sticker/闪照"。
2. **存盘**：`sha256` 命名，落在 `data/images/<前2位>/<sha>.<ext>`；同一张图只存一份。
3. **判格式**：读文件头**魔数**（PNG/JPEG/GIF/WebP）推断真实类型，不信扩展名。
4. **打标**：**先让多模态模型看一眼画面**（2026-10-30 补的；之前只拿聊天文字猜，
   等于"有图但不认识"），把画面描述 + 上下文一起交给打标模型，输出 JSON 的 tag 数组，再用**白名单过滤**——只允许
   `happy, smile, ok, cat, animal, cute, sleepy, tired, night, sad, down, thanks, thinking, hmm`
   这 14 个词。模型乱造的词直接丢掉（有测试钉住"提示词词表 == 代码词表"）。
5. **发图**：模型在回复里写 `{{img:cat}}`，编排层解析、从文本里移除、按 tag 找图发送。
   最近 10 条内已经发过图就**静默丢弃**这个标记（不找替代图、不提示），避免刷图。
6. **安全**：路径拼好后必须 `realpath` 校验在图库目录内，防目录穿越。
7. **容量与回收**：超过 `IMAGE_MAX_COUNT` 时按"无人工标签 → 最久未用"置 `archived`
   （不再发送，但**文件保留**）。磁盘只增不减，所以留了 `/img clean` 手动回收：
   删文件 + 删行，返回张数和释放的字节数。不自动删，免得删掉你还想看的东西。
8. **补标**：/img retag 把图库里"没标签"的图逐张看一遍重新打标，每次最多 20 张。
   踩过一个坑：打标调用最初只给 80 个 max_tokens，推理模型把预算全花在思考上、
   正文为空，打出来一堆"无标签"——现在给 600。旧收藏再收到时会顺手补标一次。

## 六点五、看图与画图（2026-10-30）

**做了什么**：她能看懂你发的图片和表情包；你说"画一个"，她真能画一张发过来。

**方法**：

1. **看图不另接服务**：`deepseek-flash` 本身就是多模态的（实测能读出图上的文字）。
   收到 `image` 段 → 下载 → 存 `data/inbox/<日期>/<sha>` → 问模型"画面里是什么"
   （表情包用另一段提示词，让它连情绪一起说）→ 结果写成「（他发来一张图片：…）」
   **合进那条用户消息**。合进去而不是另插一段，是为了让记忆抽取、日摘要都能看到这张图。
2. **缓存**：描述按 `sha256` 存 `image_notes` 表，同一张图只问一次模型。
3. **失败不拖累对话**：下载失败、模型超时都只跳过这张图，聊天照常。
4. **画图**：模型在回复里写 `{{draw:画什么}}`，编排层摘掉标记、文字照常发，
   再开线程去画（默认 Pollinations，免 key，几秒出图；也可配成任意 OpenAI 兼容的
   images 接口）。画好的图落 `data/drawn/<日期>/<sha>.<ext>` 单独发过来。
   - **为什么不阻塞**：出图要 5~30 秒，等图再说话像卡住；真人也是先说"我画好了"再发图。
   - **频率闸**：`DRAW_MIN_INTERVAL_SECONDS`（默认 300 秒）内只画一张，避免刷图。
   - **提示词**：先把她的中文描述翻成画图模型的英文提示词（多一次小模型调用），
     失败就用原文；再拼统一风格后缀，保证画风稳定。
5. **提示词**：明确告诉她"你能看见他发来的图"，并给两个出口——`{{img:tag}}` 发表情包、
   `{{draw:…}}` 自己画；同时要求"别每条都画，画得不完美可以自己先吐槽"。

**顺手修的老账**：记忆卡里那条"看不到图片，只能读文字"是旧设定，已改成
"能看图，但不能自己拍照"——否则她一边看图一边说自己看不见。

**画她自己（2026-10-30 补的）**：外形按 DeepSeek 社区的「鲸鱼娘／吃白饭的蓝色大肥鱼」设定——
深蓝到浅青的渐变长发、一根呆毛、白色鳍耳、白色长袖连体衣、蓝鲸尾（下面白色）。
这段外观写死在 `qqbot/draw.py` 的 `CHARACTER` 里，她说"画我"时由代码补全，
不靠模型自己记，也不用人设里每次列一遍。

**供应商现状（2026-10-30 实测）**：免费不要 key 的只剩 Pollinations 的 `flux`
（turbo/sana 已 402，kontext/seedream 403），而且右下角会带 pollinations.ai 水印、
手和尾巴容易画糊、连续请求会被限流（402，隔一会儿重试能过）。
要明显更好的画质得填自己的 key：`.env` 里 `DRAW_PROVIDER=openai` +
`DRAW_BASE_URL`/`DRAW_MODEL`/`DRAW_API_KEY`，智谱（cogview-3-flash）和硅基流动都有免费额度。
备用命令 `/draw 一只猫` 可以不经过对话直接出图，用来试供应商。


**2026-10-30 按用户给的设定图重做外观**：原图是 iPhone 的 HEIC（扩展名写成 .png，PIL 和接口都不认），先用 pillow-heif 转成 JPEG 再喂给识图模型提取设定——深蓝→浅蓝渐变长卷发、齐刘海、弯呆毛、亮蓝大眼、蓝色鳍耳（耳根蝴蝶结）、深蓝女仆裙 + 白蕾丝围裙（绣小鲸鱼）、分叉鲸尾、Q 版约 2.5 头身。

**2026-10-30 活人感返工**：用户问「活人感够不够」，统计了 98 条她说的话——最近 15 条还行
（平均 19 字、没有「唔」开头），但整段仍有三个硬伤：①全部围绕他，没有自己的日子；
②看图像念 OCR（「上面写着 HAPPY，下面还有 placeholder」）；③太会接话、太乖。
改了三处：

1. **生活线**（`qqbot/life.py`）：每天生成 4 行「她今天的日子」（做了什么、小麻烦、手边有什么、
   想提的一件小事），存 `data/life/YYYY-MM-DD.md`，随 prompt 注入，也允许她不提。
   实测：问「你干嘛呢」→「啃饼干 ／ 第三块了，晚饭还没着落」，不再只会反问。
2. **杀 OCR 腔**：看图提示词改成「先说人话，最多补一句细节，别逐字念字」。
3. **称呼清洗**（`formatting.fix_address`）：记忆本、日摘要、以及她自己说过的历史消息里的
   「爸爸」统一换成「你」——旧称呼回灌 prompt 会被模型学着叫（曾 7/98 条中招）。

顺带修了生活线健壮性：模型偶尔像聊天一样回「好呀。」，这种结果不落盘。


**2026-10-30 口语化 + 梗 + 随手表情包**：用户说"太正式、不地道"，要求懂梗、会用梗、偶尔甩表情包。

- **口头语库**（`qqbot/slang.py`）：36 条 2024–2026 还在用的梗（已老实/破防/啊这/麻了/哈基米…）
  + 8 个插话词（就是说/反正/属于是…）+ 一份"过时禁词"（绝绝子/yyds/干饭人…）。
  按日期固定抽 10 条注入，同一天内不换批，避免每条消息都换风格。
- **prompt**：加"别用书面词"（或许/其实/应该/非常）和"每五六条至少用一个口头语"；
  补了带梗的对话样品；新增「说人话」小节，直接给"我觉得你可能是有点累了 → 累了吧"这种改写。
- **随手表情包**：`STICKER_CHANCE`（默认 0.12），回完话有概率自己甩一张，不发文字解释；
  tag 从 `STICKER_TAGS` 里随机挑图库里有的，发过图的冷却期内不发。
- **取材说明**：本想抓公开梗列表，但这台机器的 DNS 把域名解析到 198.18.x.x（只放行模型 API），
  网页全抓不到，只拿到搜索标题；梗表是人工筛的，来源记在 `prompts/slang.md`。


**2026-10-30 看电脑（/screen、/pc）**：用户问"她怎么访问我的电脑"，做了命令触发式的只读访问。

- `qqbot/pc.py`：截图走 PowerShell + `System.Drawing.CopyFromScreen`（VirtualScreen，多屏一起），
  状态走 `Get-CimInstance` + `GetForegroundWindow`（前台窗口标题）；缩图用 Pillow（156KB → 68KB JPEG）。
- `/screen`：截图 → 发给他 → 让她看着说一句（`_react_to` 单独调用，不进历史）。
- `/pc`：CPU/内存/C 盘/开机时长/电量/前台窗口/内存 top3，让她就着说一句；`/pc 详细` 回原始数据。
- 边界写在 `docs/PC_ACCESS.md`：不自动截、不留超过 20 张、不做任意命令执行。
- 实测这台机器：CPU 9%、内存 91%（15GB 剩 1GB）、C 盘剩 3.5GB —— C 盘确实快满了。


**2026-10-30 陪玩（/watch）**：用户选了"她坐旁边看你打游戏"这一档。

- `/watch` 起一个后台线程：每 `WATCH_INTERVAL_SECONDS`（默认 75 秒，±25% 抖动）截一张屏，
  画面指纹没变就不吭声（`pc.frame_hash` + `pc.changed`，16×16 灰度，差 12 位以上才算变），
  变了才让视觉模型看一眼，再让她说一句 20 字以内的话；说过的话会回喂"别重复"。
- 上限：`WATCH_MINUTES`（30 分钟）、`WATCH_MAX_LINES`（20 句），`/watch 停` 随时打断。
- 实测三次：`这表格看得我眼睛都花了` → `你忙你的，我就在这儿趴着` → `我趴着趴着快睡着了`。
- 注意：陪玩期间发的消息 `origin=watch`，走 `_send_lock`，不会和正常回复插队。

## 七、主动消息（M4）

**做了什么**：她会先开口——两种情形。

**方法**：

1. **`scheduled`（未来事件）**：记忆抽取时，如果对话里提到"下周三面试"这类将来的事，
   额外输出 `events`，含 `summary` + `due_at`（`YYYY-MM-DD HH:MM`）。
   相对时间（"下周三"）由模型按【当前时间】换算成绝对日期。
   **解析不出具体时间的一律丢弃**——猜错日子比不提醒更糟。
   到点后走同一套发送链路。
2. **`followup`（长期沉默）**：72 小时没说话 + 7 天内没主动过，从记忆里找话题开口。

**闸门**（缺一不可，防骚扰/防风控）：

```
每天 ≤ 3 条  ·  只在 09:00–23:00  ·  两条间隔 ≥ 4 小时
用户最近 30 分钟说过话 → 不发   ·  她上次主动你没回 → 不连着追
followup 每周 ≤ 1 次          ·  发送失败不重试
```

**模型可以拒绝**：生成时允许只输出 `SKIP`，表示"这会儿不想说"。
这样她不是定时脚本，而是每次都做一次判断。

**情绪 / 驱力状态**：她有"此刻"，`/mood` 可看。

```
想念 miss  ·  亲近 warmth  ·  疲惫 tired      （都是 0~1）
```

- 每个值朝"目标"做**指数逼近**（半衰期：想念 3h、亲近 24h、疲惫 3h），
  目标由时间和事件算出来：多久没说话 → 想念；夜里 → 疲惫；他说话 → 想念落地、亲近涨
- **没有心跳线程**：读的时候按流逝时间补算，只在事件（他说话）时落库，
  重启不丢，也不会空转
- 注入 system prompt 的「# 此刻的你」，只在极端值加一句行为暗示
  （很想他 → 可以主动问一句但别腻；累了 → 句子短一点）
- 接进主动消息闸门：`tired ≥ 0.7` 直接不开口；`miss ≥ 0.75` 把"多久没聊"的门槛打到 0.6 倍
- **共情**：读他这条消息的情绪（词表法，6 类：难过/不安/生气/孤单/累/开心），
  **赶在回复之前**生效——影响她的亲近/疲惫，并把一句行为提示写进 prompt
  （"他听着不太好受：先陪着，别讲道理"；"他累了：话短一点"）。
  半小时内有效，过后自动失效。
  用词表而不是再调一次模型，是因为要赶在回复前 + 判定要可解释；
  代价是读不出反讽，所以它只做**微调**，错了顶多语气偏一点。
  匹配前会抹掉「有点 / 真的 / 特别」这类程度词——"心里有点堵"和"心里堵"是同一句话。
  这条是真机验证时才补的：第一版对着"心里有点堵"完全没反应。

## 八、稳定性

**做了什么**：夜里挂了能自己起来，协议端假在线能报出来。

**方法**：

1. **看门狗**：每 5 分钟调一次 `get_friend_list`。
   关键教训：`get_status` 会骗人——QQ 内核断网时它照样返回 `online: true`，
   而 `get_friend_list` 会返回空数组。所以探测用后者，空列表也当成故障。
   连续 2 次失败报一条警告（同一故障只报一次，恢复后重置）。
2. **启动等网络**：开机自启时模型 API 常常还不可达，先探一次，
   最多等 `NETWORK_WAIT_SECONDS`（默认 30 秒）再开始服务。
3. **文件日志**：滚动写到 `logs/bot.log`，所有失败都带原因（模型调用失败会记每次重试的原因）。
4. **一键重启协议端**：`scripts/restart-napcat.bat`，自动提权、只杀 NapCat 进程树、
   不动你自己的 QQ、重启后等 60 秒确认活着。
5. **失败回复重放**：发送失败的行留在 `messages` 里（`send_state='failed'`、`origin='reply'`），
   后台线程每 60 秒扫一次，**只补 10 分钟内、最多 3 次**，成功改状态、失败累加次数，
   超次数置 `dead`。重放不新建行，所以"不丢不重"。主动消息不重放——隔几小时冒出来是骚扰。
6. **启动自检模型**：启动时真调一次模型。今天踩过：换了 `.env` 的 key 但没重启，
   进程拿着旧 key，用户只收到兜底话术，日志里才有 401。现在失败会明确写 ERROR。
7. **上报即应答**：HTTP 线程只入队并立刻回 204，处理交给单线程队列。
   NapCat 的 `baseTimeout` 只有 10 秒，等处理完再应答就会被判超时重推。
8. **幂等靠抢占式写入**：先落库占位再干网络 IO，写入失败即视为重复消息。

## 九、消息格式

**方法**：

- **分段**：超过 300 字按句子切段，段间延迟发送（长消息容易被折叠，也更容易风控）。
- **清洗**：模型爱写 Markdown，发 QQ 前 `strip_markdown` 去掉 `**`、`#`、列表符号。
- **例外**：指令回复（`/img list` 之类）**不走清洗**——
  之前编号 `7. ` 被当成有序列表剥掉，吃过这个亏。
- **不显示"正在输入"**：明确不做输入状态，避免假感。
