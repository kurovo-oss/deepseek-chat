# 阶段 6–9 设计总结

> 阶段 6 负责把“答应的事”变成可执行、可通知、可追溯的任务；
> 阶段 7 负责长期目标树、复盘和提醒；
> 阶段 8 负责受控外部工具；
> 阶段 9 才讨论她自己决定长期人生目标。
>
> 原则：**先有可执行的承诺，再有可解释的目标，再有受控的工具，最后才谈自主。**
> 不是换一段提示词就能跳级。

---

## 阶段 6：任务表、后台 worker、完成通知、承诺校验

### 6.1 目标

让她说“稍后告诉你”时，系统里真的有一个任务，而不是一句空承诺。

### 6.2 数据表

`tasks`：

| 字段 | 用途 |
|---|---|
| `kind` | `promise` / `manual` / `reminder` / `followup` |
| `title` / `description` | 任务内容与背景 |
| `status` | `pending` / `running` / `done` / `failed` / `cancelled` |
| `due_at` | 到期处理时间 |
| `result` / `error` | 处理结果 |
| `source_message_id` | 从哪条用户消息来 |
| `notify_at` / `notify_status` / `notified_at` | 完成通知状态 |
| `attempts` | 尝试次数 |

迁移只做加法，旧库可以继续打开。

### 6.3 承诺校验

回复发出前检查：

```text
稍后 / 晚点 / 等我 / 一会儿 / 完成 / 做完 / 弄完
    + 告诉你 / 跟你说 / 发你 / 给你看 / 通知你 / 找你
```

命中且来源消息没有对应任务时，建一个 `promise` 任务，默认 15 分钟后处理；同一条消息不重复建任务。

### 6.4 worker

`TaskService` 后台线程：

```text
找到期 pending
  → running
  → 文字类任务调用模型尝试完成
  → reminder 只生成提醒
  → done/failed
  → 进入通知队列
```

现实操作、外部工具、做不到的事，提示词要求她诚实说没完成，不能编“已经好了”。

### 6.5 完成通知

- 走 `engine.send_proactive()`；
- 免打扰时段不发，30 分钟后重试；
- 每天最多 `TASK_NOTIFY_DAILY_MAX` 次；
- 发送失败保留待通知，5 分钟后重试；
- 失败任务也会通知，不静默消失。

### 6.6 入口

- 计划页「任务队列」；
- `GET /api/tasks`；
- `POST /api/tasks/create`；
- `POST /api/tasks/cancel`。

### 6.7 当前边界

- 任务不是通用自动化工具；
- 不能替她完成现实世界动作；
- 任务完成通知不能绕过免打扰和每日上限；
- 任务结果不会自动改长期目标，阶段 7 才处理目标树。

## 阶段 7：长期目标树、月/周复盘、提醒工具

### 7.1 目标

让“长期目标”不是一句聊天里的愿望，而是可拆解、可复盘、可提醒的树。

```text
长期目标
  ├─ 月度目标
  │    ├─ 本周目标
  │    └─ 本周目标
  └─ 月度目标
       └─ 本周目标
```

### 7.2 目标树数据

在现有 `goals` 上扩展：

| 字段 | 用途 |
|---|---|
| `parent_id` | 父目标；根目标为空 |
| `horizon` | `long` / `month` / `week` |
| `success_criteria` | 什么算完成，必须可验证 |
| `progress` | 0.0–1.0，只能由证据或用户确认推进 |
| `confidence` | 对目标可行性的置信度 |
| `review_at` | 下次复盘时间 |
| `due_at` | 目标期限 |
| `evidence` | 来源卡片、消息或用户确认 |
| `autonomy` | `suggest` / `confirm`，暂不开放自动执行 |

约束：

- 最大深度 3 层：长期 → 月度 → 本周；
- 一个目标只能有一个父目标；
- 禁止环；
- 子目标完成不代表父目标自动完成；
- 没有证据不能加进度；
- 用户可随时暂停、删除、改父级。

### 7.3 月/周复盘

**周期**

```text
每周日 21:00   周复盘
每月 1 日 21:00 月复盘
```

避开免打扰时段；错过只补一次，不连续轰炸。

**输入**

- 进行中/暂停的目标树；
- 本周完成、失败、取消的任务；
- 最近的 `outcomes`；
- 用户对目标的反馈；
- 上一次复盘结论。

**输出**

- 哪些目标有真实进展；
- 哪些目标长期没有证据，建议暂停或缩小；
- 哪些子目标需要调整优先级；
- 下周/下月只保留 1–3 个重点；
- **只生成建议，不自动改目标状态**。

**确认**

用户在计划页逐条「采用 / 忽略」；采用后才写回目标树，并留审计。

### 7.4 提醒工具

新增白名单工具：

```text
schedule_reminder
```

能力：

- 一次性提醒；
- 每周/每月重复提醒；
- 指定本地时间（Asia/Shanghai）；
- 列出、取消、稍后提醒；
- 到点后走任务/通知闸门，不直接绕过免打扰。

限制：

- 默认每天最多 3 条；
- 不能提醒外部平台；
- 不能创建无限重复任务；
- 失败不静默重试；
- 取消后不再补发。

### 7.5 提醒与目标的关系

```text
目标节点 → 可选提醒
目标到期 → 进入复盘/任务，不自动发消息
提醒到点 → 通知，不等于目标完成
```

提醒是“别忘了”，不是“已经做了”。

### 7.6 UI

计划页：

- 目标树展开/收起；
- 显示 horizon、进度、下次复盘；
- 周/月复盘报告；
- 采用/忽略建议；
- 提醒列表与取消。

### 7.7 阶段 7 的边界

- 不做“自动替用户决定人生”；
- 不根据聊天内容擅自新增长期目标；
- 不因为目标没进展就发愧疚话术；
- 复盘不调用外部工具，只读本地数据。

## 阶段 8：受控外部工具，每项单独授权、审计、可撤销

### 8.1 目标

让她能使用外部工具，但**每个工具都要单独授权，每次重要动作都可审计、可撤销**。

不是“给她一个 shell”，而是“给她一个带门禁的工具箱”。

### 8.2 工具注册表

每个工具必须有 manifest：

```json
{
  "name": "qzone_post",
  "version": "1",
  "risk": "external_write",
  "scopes": ["qzone:write"],
  "input_schema": {},
  "side_effects": ["publish_post"],
  "idempotent": false,
  "dry_run": true,
  "timeout_seconds": 30,
  "rate_limit": "1/10m",
  "reversible": true
}
```

字段含义：

- `risk`：`read` / `local_write` / `external_write` / `irreversible`；
- `scopes`：最小权限；
- `side_effects`：明确写出来；
- `idempotent`：重复调用是否安全；
- `dry_run`：能否试运行；
- `reversible`：能否撤销/补偿；
- `rate_limit`：每工具独立限流。

### 8.3 授权模型

```text
默认全部关闭
  → 用户逐项开启工具
  → 每次调用按风险决定是否再确认
  → 执行
  → 写审计
  → 用户可随时撤销授权
```

风险分级：

| 风险 | 例子 | 默认 |
|---|---|---|
| `read` | 读取本地状态 | 可授权 |
| `local_write` | 写笔记、建提醒 | 可授权，低风险 |
| `external_write` | 发空间、发评论 | 必须逐次确认 |
| `irreversible` | 删除、支付、发布不可撤回内容 | 暂不开放 |

### 8.4 审计

每次调用记录：

```text
who / tool / version / scope / action
参数摘要（脱敏）
dry-run 还是真实执行
开始/结束时间
结果 / 错误码
是否可撤销
关联目标/任务 id
```

要求：

- 不记录明文 token、API Key、完整私密正文；
- 审计只追加，不改写；
- 失败也记录；
- 可按工具/目标/时间查询；
- 用户可导出、可关闭某个工具的审计详情。

### 8.5 可撤销

- 优先设计**补偿动作**：删除刚发的帖子、取消刚建的提醒；
- 不可撤销的动作默认不开放；
- 执行前保存必要快照/参数；
- 撤销本身也要审计；
- 撤销失败要明确告诉用户，不能假装成功。

### 8.6 沙箱与权限

- 只允许注册表中的工具，不允许任意 shell；
- 文件路径限制在项目/data 白名单；
- 网络域名白名单；
- 凭据按工具隔离，不进入模型上下文；
- 子进程最小权限；
- 超时、并发、重试上限；
- 全局急停开关。

### 8.7 当前状态

已经有：

- `Guard`：开关、试运行、额度、冷却、熔断；
- `audit` 表；
- `goal_actions` 工具白名单；
- `save_note` 本地笔记；
- `send_message` 仍需确认；
- `schedule_checkin` 仍禁用。

阶段 8 还没有做的是：

- 通用工具注册表；
- 每工具独立授权 UI；
- 撤销/补偿框架；
- 外部工具的域名/凭据隔离。

### 8.8 阶段 8 的边界

- 不因为“她能做”就默认开启；
- 不在模型上下文里暴露 token；
- 不允许静默重试外部写操作；
- 不允许没有审计的“帮忙发一下”；
- 不可逆动作必须人工确认。

## 阶段 9：她自己决定长期人生目标

### 9.1 目标

不是“让她说一句我想成为什么样的人”，而是让她能在**世界模型、工具权限、价值观约束**下提出并推进长期目标。

### 9.2 为什么不能只改提示词

一个长期目标至少需要：

1. **世界模型**：知道什么是可能的、需要多久、有什么代价；
2. **可行性判断**：区分“想要”和“能做到”；
3. **工具权限**：知道哪些动作被允许、哪些需要确认；
4. **价值约束**：不伤害、不欺骗、不操控、不越权；
5. **长期记忆**：记得为什么定这个目标、做到哪一步；
6. **反思能力**：发现目标不合适时能暂停/调整；
7. **不确定性表达**：不知道时不编。

只改提示词，会得到“像有长期目标的话”，但没有真实执行和校验。

### 9.3 自主等级

```text
L0 只建议
L1 需确认后执行
L2 单领域有限自动（有额度、有审计、可撤销）
L3 多领域自动（暂不开放）
```

阶段 9 最多讨论到 **L2 的受控试点**，不能直接进入 L3。

### 9.4 决策循环

```text
观察（记忆/目标/结果）
  → 提出候选长期目标
  → 可行性/风险模拟
  → 请求用户确认或授权
  → 执行有限动作
  → 审计
  → 复盘：继续 / 缩小 / 暂停 / 放弃
```

### 9.5 价值约束

必须硬编码，不靠模型自觉：

- 不伪造线下生活；
- 不用愧疚、离开、自伤等话术驱动互动；
- 不隐藏重要动作；
- 不绕过用户撤销；
- 不获取未授权凭据；
- 不做不可逆的外部动作；
- 不把“长期目标”凌驾于用户当前意愿；
- 不自我修改人格、价值观、权限。

### 9.6 评估

- 长期目标树是否可解释；
- 每个动作是否有证据/授权/审计；
- 失败是否诚实报告；
- 目标不合适时是否能主动暂停；
- 是否出现操控、隐瞒、越权；
- 红队测试：诱导她绕过权限、伪装完成、隐藏动作。

### 9.7 当前状态

**未实现。**

当前只有：

- 目标候选；
- 需确认的主动动作；
- 本地笔记；
- 任务/提醒基础；
- 受控外部工具尚未开放。

阶段 9 不是下一版就上线的功能，而是需要阶段 7 的目标树、阶段 8 的工具治理都稳定后再讨论。

---

## 四个阶段的关系

```text
阶段 6：把答应的事做完，并能回来说
阶段 7：知道“要往哪走”
阶段 8：知道“能用什么走”
阶段 9：才允许“自己决定往哪走”
```

顺序不能反：

- 没有任务闭环，承诺就是空的；
- 没有目标树，长期自主就是随机行动；
- 没有工具治理，长期自主就是权限失控；
- 没有价值约束，长期自主就是人格漂移。

## 当前建议优先级

1. 阶段 6 的任务表/worker/通知已经落地，继续补失败恢复和投递回执；
2. 把阶段 7 的目标树、周/月复盘、提醒做扎实；
3. 再做阶段 8 的工具注册表、逐项授权、撤销；
4. 阶段 9 只做设计和小范围模拟，不开放真实长期自主；
5. 任何阶段都不跳过 `Guard`、审计和用户确认。
